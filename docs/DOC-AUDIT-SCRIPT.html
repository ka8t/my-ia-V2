Vue d'ensemble — Section 1

Le script d'audit analyse automatiquement le code source pour détecter les problèmes de sécurité, architecture, interface, UX et maintenance. Il génère un rapport HTML interactif avec visualisations et comparaison historique.

Fonctionnalités principales

🛡 Sécurité OWASP
SQL Injection, XSS, secrets hardcodés, HTTP sans TLS, routes non protégées
🏗 Architecture
Logique DB dans routers, queries N+1, séparation des responsabilités
🎨 Interface
innerHTML non sécurisé, styles inline, SVG inline, manipulation DOM
🔔 Expérience utilisateur
Toasts non traduits, console.log, accessibilité (aria-label)
♻ Maintenance
TODO/FIXME, code mort, dette technique
📊 Rapports
HTML interactif, graphiques, historique, comparaison baseline

Flux d'exécution

⚙ Config → 🧪 Fixtures → 🔍 Scan → 🧪 Tests → 📊 Baseline → 📄 Rapport

Premier lancement

# Premier lancement : crée audit.config.json depuis le template
python scripts/run_audit.py
# → Fichier créé, le script s'arrête pour vous permettre de configurer

# Après configuration : lancer l'audit
python scripts/run_audit.py

Configuration obligatoire : Si audit.config.json n'existe pas, le script le crée depuis audit/audit.config.template.json puis s'arrête (exit 0). Modifiez le fichier selon votre projet avant de relancer.

Configuration — Section 3

La configuration est chargée avec la priorité suivante :

1. Options CLI → 2. Variables ENV → 3. audit.config.json → 4. Défauts
Pourquoi cet ordre ? La priorité va du plus spécifique au plus général :
  • Options CLI — Pour un override ponctuel lors d'une exécution spécifique (ex: --quick pour un audit rapide)
  • Variables ENV — Pour les environnements CI/CD où la config varie selon le pipeline, ou pour des préférences de session
  • audit.config.json — Pour les paramètres persistants du projet, commités dans le repo et partagés par l'équipe
  • Défauts — Valeurs raisonnables pour que le script fonctionne sans configuration

Poids des catégories

Les poids affectent le calcul du score de santé :

Score = Σ(succès × poids) / Σ(total × poids) × 100

Exemple avec poids par défaut :
- Security (poids 3) : 10 findings → impact ×3
- UI (poids 1) : 10 findings → impact ×1

Utilisation CLI — Section 4

Syntaxe

python scripts/run_audit.py [OPTIONS]
⚠ Répertoire courant — Le script doit être lancé depuis la racine du projet. Le fichier audit.config.json est recherché dans le répertoire courant (os.getcwd()), pas dans le dossier du script. 
# ✔ Correct
cd /path/to/my-ia
python scripts/run_audit.py

# ❌ Incorrect (config non trouvée)
cd /tmp
python /path/to/my-ia/scripts/run_audit.py

Options disponibles

OptionCourtDescription
--config=FILE-cFichier de configuration JSON
--project=NAME-pNom du projet (override config)
--output=DIR-oDossier de sortie des rapports
--quick-qMode rapide (sécurité uniquement)
--fail-on-highExit code 1 si HIGH trouvé
--self-testValide les fixtures, exit 2 si invalides
--disable-rule=RULEDésactiver une règle (répétable)
--only-category=CATUne seule catégorie
--verbose-vMode verbose

Exemples d'utilisation

# Audit complet
python scripts/run_audit.py

# Audit rapide (sécurité uniquement)
python scripts/run_audit.py --quick

# Configuration personnalisée
python scripts/run_audit.py --config=my-config.json

# Changer le nom du projet
python scripts/run_audit.py --project="Mon Application"

# Désactiver des règles spécifiques
python scripts/run_audit.py --disable-rule="TODO/FIXME" --disable-rule="console.log"

# Audit d'une seule catégorie
python scripts/run_audit.py --only-category=security

# CI/CD : échouer si vulnérabilités critiques
python scripts/run_audit.py --fail-on-high

# Valider les fixtures (CI/CD)
python scripts/run_audit.py --self-test --quick

Codes de sortie

CodeSignificationDétail
0SuccèsSeuils respectés, ou config créée depuis template
1Seuil dépasséTrop de HIGH (le rapport est quand même généré)
2Fixtures invalidesAvec --self-test : détection défaillante
Comportement des seuils : Le rapport HTML est toujours généré, même si les seuils sont dépassés. Le code de sortie permet au CI/CD de bloquer le pipeline après génération du rapport.

Règles de détection — Section 6

Structure d'un finding

Chaque problème détecté contient :

{
  "category": "SECURITY",
  "rule": "SQL Injection",
  "file": "app/features/users/service.py",
  "line": 42,
  "code": "query = f\"SELECT * FROM users WHERE id = {user_id}\"",
  "severity": "HIGH",
  "risk": "Permet l'exécution de code SQL arbitraire",
  "solution": "Utiliser des paramètres liés",
  "benefit": "Immunité contre les injections SQL",
  "confidence": 95
}

Niveaux de sévérité

NiveauCouleurDescriptionAction
HIGHRougeVulnérabilité critiqueCorriger immédiatement
MEDIUMOrangeProblème importantPlanifier la correction
LOWBleuAmélioration suggéréeCorriger si possible

Score de confiance

Chaque détection a un score de confiance (0-100) :

  • 90-100 : Détection certaine
  • 70-89 : Probable, à vérifier
  • 30-69 : Possiblement un faux positif

Désactiver une règle

# Via CLI
python scripts/run_audit.py --disable-rule="TODO/FIXME"

# Via config
{
  "rules": {
    "disabled": ["TODO/FIXME", "console.log"]
  }
}

Fixtures & Tests — Section 7

Les fixtures permettent de valider que les règles de détection fonctionnent correctement.

Structure des fixtures

tests/audit/fixtures/
├── vulnerable/          # 23 fichiers avec failles (doivent être détectés)
│   ├── sql_injection_fstring.py
│   ├── xss_innerhtml.js
│   └── ...
└── clean/               # 19 fichiers sains (ne doivent PAS être détectés)
    ├── sql_parameterized.py
    ├── xss_with_templates.js
    └── ...

Mapping des fixtures

Défini dans tests/audit/conftest.py :

VULNERABLE_FIXTURES = {
    "sql_injection_fstring": ("sql_injection_fstring.py", "app/service.py", "SQL Injection"),
    "xss_innerhtml": ("xss_innerhtml.js", "UI-FRONT/js/app.js", "XSS"),
    # ...
}

CLEAN_FIXTURES = {
    "sql_parameterized": ("sql_parameterized.py", "app/service.py", "SQL Injection"),
    # ...
}

Validation des fixtures

# Valider que toutes les fixtures sont correctement détectées
python scripts/run_audit.py --self-test --quick

# Résultat attendu
   ✅ Fixtures: 100.0% (23/23 vulnérables détectés, 19/19 clean validés)

Métriques de validation

MétriqueDescriptionObjectif
True PositivesVulnérables correctement détectés23/23
True NegativesClean correctement ignorés19/19
False NegativesVulnérables non détectés0
False PositivesClean détectés à tort0
Important : Si des fixtures échouent, cela indique un problème dans les règles de détection, pas dans le code audité.

Intégration CI/CD — Section 9

GitHub Actions

name: Audit de sécurité

on: [push, pull_request]

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Setup Python
        uses: actions/setup-python@v4
        with:
          python-version: '3.11'

      - name: Run Audit
        run: python scripts/run_audit.py --fail-on-high --quick

      - name: Upload Report
        uses: actions/upload-artifact@v3
        with:
          name: audit-report
          path: docs/audit-reports/*.html

GitLab CI

audit:
  stage: test
  script:
    - python scripts/run_audit.py --fail-on-high
  artifacts:
    paths:
      - docs/audit-reports/
    expire_in: 1 week
  rules:
    - if: $CI_MERGE_REQUEST_ID

Pre-commit hook

#!/bin/bash
# .git/hooks/pre-commit

python scripts/run_audit.py --quick --fail-on-high
if [ $? -ne 0 ]; then
    echo "❌ Audit échoué - corrigez les vulnérabilités HIGH"
    exit 1
fi
