1 Vue d'Ensemble

MY-IA V2 est une stack 100% Python : un seul container app sert à la fois le HTML (Jinja2 + HTMX + Alpine.js) et l'API JSON versionnée (/api/v1/*). Les anciens containers JS séparés (UI-FRONT, UI-BACK) ont été supprimés au cutover (Phase 4.d/e, mai 2026).

6 Sécurité & Chiffrement

Chiffrement PII (AES-256-GCM)

# app/common/crypto/encryption.py

class EncryptionService:
    """
    Chiffrement AES-256-GCM pour données personnelles.
    - IV aléatoire unique par opération (12 bytes)
    - Tag d'authentification (16 bytes)
    - Format stocké: IV || Ciphertext || Tag (base64)
    """

    def encrypt(self, plaintext: str) -> str:
        iv = os.urandom(12)  # Nonce unique
        cipher = Cipher(
            algorithms.AES(self.key),
            modes.GCM(iv),
            backend=default_backend()
        )
        encryptor = cipher.encryptor()
        ciphertext = encryptor.update(plaintext.encode()) + encryptor.finalize()
        return base64.b64encode(iv + ciphertext + encryptor.tag).decode()

Données chiffrées : Prénom / Nom, Téléphone, Adresse, Autres PII configurables

Le frontend V2 est rendu côté serveur via Jinja2. HTMX gère les interactions dynamiques (swap partiels, SSE chat). Alpine.js apporte le state local (modals, toggles, sélections multiples).

Conventions clés

  • Aucune génération de DOM en JS : tout HTML est rendu par Jinja, soit en page complète, soit en partial swap-é par HTMX.
  • Macros mutualisées : avant de créer un template, vérifier templates/macros/.
  • Alpine.js réservé aux modals, dropdowns, sélection multiple (Set), pas de state global.
  • CSRF : token rotatif par session, validé sur tous les POST/PUT/PATCH/DELETE web.
  • i18n : {{ t('cle') }} utilise automatiquement user_lang du contexte (helper @pass_context). Fallback FR.
  • Thème : <html data-theme="auto|light|dark"> lu depuis la préférence user en session.
  • Streaming chat : SSE via htmx-ext-sse + marked.js au close pour rendu Markdown progressif.

Configuration SSL — Let's Encrypt (Production)

V2 prod utilise nginx système avec Let's Encrypt sur my-ia.codefixture.com. Le container app écoute en HTTP sur 127.0.0.1:8090, nginx fait la terminaison SSL et le reverse-proxy.

# Sur le VPS — installation nginx + certbot
sudo apt install nginx certbot python3-certbot-nginx
sudo certbot --nginx -d my-ia.codefixture.com

# Config nginx (extrait, /etc/nginx/sites-available/my-ia.codefixture.com)
server {
    server_name my-ia.codefixture.com;
    client_max_body_size 100m;

    location / {
        proxy_pass http://127.0.0.1:8090;
        proxy_set_header Host $host;
        proxy_set_header X-Real-IP $remote_addr;
        proxy_set_header X-Forwarded-For $proxy_add_x_forwarded_for;
        proxy_set_header X-Forwarded-Proto $scheme;
        proxy_read_timeout 300s;       # SSE chat
        proxy_buffering off;            # SSE flush immédiat
        proxy_set_header Connection ''; # SSE keep-alive
        proxy_http_version 1.1;
        proxy_cache off;
    }

    listen 443 ssl;       # managed by Certbot
    ssl_certificate     /etc/letsencrypt/live/my-ia.codefixture.com/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/my-ia.codefixture.com/privkey.pem;
}

# Redirect 80 → 443 ajouté automatiquement par certbot.

V2 réutilise les volumes V1 (BDD + ChromaDB) sans migration. Le compose V2 monte le network my_ia_internal de V1 comme network externe :

# docker-compose.yml V2
networks:
  internal:
    driver: bridge
  external:
    driver: bridge
  v1_internal:                # Phase 4.d cutover : accès BDD/Chroma V1
    external: true
    name: my_ia_internal      # Network créé par my-ia v1

# Storage uploads V1 monté en symlink dans data/uploads V2 :
ln -sfn /home/debian/my-ia/data/uploads /home/debian/my-ia-v2/data/uploads
