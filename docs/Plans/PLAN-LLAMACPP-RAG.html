Plan d'implémentation RAG avec llama.cpp

Parité fonctionnelle avec Ollama pour l'application MY-IA

1. Introduction

Objectif

Implémenter un système RAG complet avec llama.cpp qui offre les mêmes fonctionnalités que le provider Ollama :

  • Chat avec un modèle LLM (génération de texte)
  • Recherche sémantique dans les documents (embeddings)
  • Combinaison des deux pour le RAG (Retrieval-Augmented Generation)

Contrainte technique

llama-server (llama.cpp) ne peut charger qu'un seul modèle en mémoire à la fois.

Pour avoir chat + embeddings, il faut deux instances de llama-server sur des ports différents.

Provider Gestion des modèles Complexité
Ollama Automatique (charge/décharge selon besoins) Simple
llama.cpp 1 modèle par instance → 2 instances nécessaires Plus complexe

2. Concepts fondamentaux

2.1 Qu'est-ce qu'un LLM (Large Language Model) ?

Un LLM est un modèle de langage entraîné sur des milliards de textes. Il peut :

  • Comprendre et générer du texte en langage naturel
  • Répondre à des questions avec ses connaissances d'entraînement
  • Raisonner, résumer, traduire, coder...

Exemples : Qwen, Llama, Mistral, Gemma, Phi...

Limitation : Ne connaît que ce qu'il a appris pendant l'entraînement (pas vos documents).

2.2 Qu'est-ce qu'un Embedding ?

Un embedding est une représentation vectorielle (liste de nombres) d'un texte qui capture son sens sémantique.

"Les congés sont de 25 jours"  →  [0.12, -0.45, 0.78, 0.33, ...]
                                        │
                                   768 dimensions
                                   (varie selon le modèle)

Propriété clé : Des textes avec un sens similaire ont des vecteurs proches.

"Combien de jours de vacances ?"  →  [0.11, -0.44, 0.79, 0.32, ...]
                                            ↑
                                      Très proche du premier !

Exemples de modèles : nomic-embed-text, BGE, all-MiniLM, GTE...

2.3 Comment fonctionne le RAG ?

RAG = Retrieval-Augmented Generation

Combine la recherche dans vos documents + les connaissances du LLM :

└─────────────────────────────────────────────────────────────────────────────┘

2.4 Pourquoi deux modèles différents ?

Modèle Rôle Optimisé pour Taille typique
LLM (Chat) Générer du texte, répondre Compréhension, raisonnement, rédaction 0.5 - 7 GB
Embedding Transformer texte → vecteur Similarité sémantique, recherche 20 - 100 MB

Un modèle de chat peut générer des embeddings, mais la qualité est médiocre. Les modèles d'embedding sont spécialement entraînés pour cette tâche.

4.2 Le problème actuel

Le provider LlamaCppProvider utilise une seule URL (http://host:8085) pour :

  • /v1/chat/completions → génération de texte
  • /v1/embeddings → génération d'embeddings

Mais llama-server ne peut avoir qu'un modèle chargé. Si c'est un modèle de chat, les embeddings échouent (erreur pooling type 'none').

class LlamaCppProvider(LLMProvider):
    def __init__(
        self,
        # Instance CHAT
        chat_host: Optional[str] = None,
        chat_port: Optional[int] = None,

        # Instance EMBEDDING
        embed_host: Optional[str] = None,
        embed_port: Optional[int] = None,

        # Modèles
        llm_model: Optional[str] = None,
        embed_model: Optional[str] = None,

        timeout: Optional[float] = None,
    ):
        # URLs distinctes
        self._chat_host = chat_host or settings.llamacpp_chat_host
        self._chat_port = chat_port or settings.llamacpp_chat_port
        self._embed_host = embed_host or settings.llamacpp_embed_host
        self._embed_port = embed_port or settings.llamacpp_embed_port

        self._chat_url = f"http://{self._chat_host}:{self._chat_port}"
        self._embed_url = f"http://{self._embed_host}:{self._embed_port}"

        # ... reste du code

    async def generate(self, ...):
        # Utilise self._chat_url
        response = await client.post(
            f"{self._chat_url}/v1/chat/completions",
            ...
        )

    async def get_embeddings(self, text: str, model: Optional[str] = None):
        # Utilise self._embed_url
        response = await client.post(
            f"{self._embed_url}/v1/embeddings",
            ...
        )

5.4 Health check dual

Fichier : app/common/llm/llamacpp.py

async def health_check(self) -> Dict[str, Any]:
    """Vérifie la santé des deux instances llama-server."""

    chat_status = await self._check_instance(self._chat_url, "chat")
    embed_status = await self._check_instance(self._embed_url, "embedding")

    return {
        "status": "healthy" if chat_status["ok"] and embed_status["ok"] else "degraded",
        "provider": self.provider_name,
        "instances": {
            "chat": {
                "url": self._chat_url,
                "status": chat_status["status"],
                "model": chat_status.get("model"),
            },
            "embedding": {
                "url": self._embed_url,
                "status": embed_status["status"],
                "model": embed_status.get("model"),
            }
        }
    }

# PID files séparés

start_instance() {
    local instance_type="$1"  # "chat" ou "embed"

    local port=$CHAT_PORT
    local pid_file=$CHAT_PID_FILE
    local embed_flag=""

    if [[ "$instance_type" == "embed" ]]; then
        port=$EMBED_PORT
        pid_file=$EMBED_PID_FILE
        embed_flag="--embedding"
    fi

    # ... logique de démarrage avec le bon port et flag
}

stop_instance() {
    local instance_type="$1"
    # ... arrêter l'instance spécifique
}

show_status() {
    echo "=== Instance CHAT (port $CHAT_PORT) ==="
    # ... statut instance chat

    echo ""
    echo "=== Instance EMBEDDING (port $EMBED_PORT) ==="
    # ... statut instance embedding
}

9.3 Test manuel rapide

# 1. Démarrer les instances
./scripts/llamacpp.sh start chat --model models/gguf/qwen2.5-0.5b-instruct-q4_k_m.gguf
./scripts/llamacpp.sh start embed --model models/gguf/nomic-embed-text-v1.5.Q4_K_M.gguf

# 2. Vérifier le statut
./scripts/llamacpp.sh status

# 3. Tester les endpoints
curl http://localhost:8085/health  # Chat
curl http://localhost:8086/health  # Embed

# 4. Tester les embeddings
curl -X POST http://localhost:8086/v1/embeddings \
  -H "Content-Type: application/json" \
  -d '{"input": "test", "model": "nomic"}'

# 5. Tester le chat
curl -X POST http://localhost:8085/v1/chat/completions \
  -H "Content-Type: application/json" \
  -d '{"model": "qwen", "messages": [{"role": "user", "content": "Bonjour"}]}'

10. Déploiement

10.1 Prérequis

  • llama.cpp compilé avec Metal (bin/llama.cpp/build/bin/llama-server)
  • Au moins un modèle GGUF de chat téléchargé
  • Au moins un modèle GGUF d'embedding téléchargé
  • Ports 8085 et 8086 disponibles

10.2 Mémoire GPU estimée

Configuration Chat Embed Total
Minimale Qwen 0.5B (400 MB) MiniLM (17 MB) ~500 MB
Recommandée Qwen 1.5B (1.1 GB) Nomic (87 MB) ~1.2 GB
Performante Llama 3B (2 GB) BGE Base (70 MB) ~2.1 GB

10.3 Ordre de déploiement

  1. Télécharger les modèles GGUF (via UI Admin ou manuellement)
  2. Configurer les clés BDD (llm.llamacpp.chat.model, etc.)
  3. Modifier llm.provider = "llamacpp"
  4. Démarrer les instances via script ou UI
  5. Vérifier le health check
  6. Tester un upload + question RAG
