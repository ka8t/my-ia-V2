Section 1

Contexte et Problème

↑ Sommaire

Situation Actuelle

Le système supporte deux providers LLM pour les embeddings :

  • Ollama — Provider cloud/local avec modèles comme nomic-embed-text
  • llama.cpp — Provider local avec modèles GGUF
⚠️
Problème critique : Les embeddings générés par Ollama et llama.cpp ont des dimensions différentes et ne sont pas compatibles dans la même collection ChromaDB.

Comportement Attendu

  • Chaque provider a sa propre collection ChromaDB (suffixe _ollama ou _llamacpp)
  • L'indexation utilise toujours le provider courant configuré dans l'admin
  • L'UI affiche uniquement les données indexées avec le provider courant
  • Le changement de provider masque les données de l'ancien provider (sans les supprimer)

Éléments Concernés

Élément Collection ChromaDB Champ Provider
Documents documents_{provider} documents.indexed_provider
Sources external_sources_{provider} context_sources.indexed_provider
Corpus corpus_{corpus_id}_{provider} corpus.indexed_provider

Règles Métier

R1 Indexation
  • Toute indexation utilise le provider courant
  • Le champ indexed_provider est mis à jour après indexation
  • Embeddings stockés dans la collection du provider courant
R2 Affichage
  • Tableaux affichent uniquement les éléments du provider courant
  • Compteurs reflètent le provider courant
  • Badge indique le provider utilisé
R3 Réindexation
  • Réindexation utilise toujours le provider courant
  • Anciennes données dans l'autre collection restent intactes
  • Champ indexed_provider est mis à jour
R4 Corpus
  • Corpus agrège documents et sources
  • Affichage contenu filtre par provider courant
  • Réindexation corpus réindexe tous les éléments

Corpus

Fichier Modification
corpus/repository.py Ajouter filtre provider pour les documents/sources liés

POST /corpus/{id}/reindex : utiliser provider courant
corpus/service.py get_corpus_content() : filtrer par provider
reindex_corpus() : indexer avec provider courant

Pattern de Récupération du Provider

Utiliser le code existant dans chaque repository/router :

# Récupérer le provider courant (déjà disponible via SystemConfigService)
config_service = SystemConfigService(db)
provider = await config_service.get("llm.embedding_provider") \
           or await config_service.get("llm.provider", "ollama")

# Nom de collection (pattern existant dans SourceIndexer)
collection_name = f"{base_collection}_{provider}"
💡
Pas besoin de créer un nouveau fichier — ces patterns existent déjà dans le code.

Section 5

Modifications Frontend Utilisateur (UI-FRONT)

↑ Sommaire

Contexte

L'interface utilisateur (chat) affiche les collections publiques disponibles pour le RAG. Ces collections doivent être filtrées par le provider courant pour n'afficher que les données compatibles avec les embeddings actifs.

⚠️
Règles métier :
  • Un utilisateur ne doit voir que les collections indexées avec le provider courant
  • Les collections sans corpus sont exclues (pas de contenu RAG)
  • Les collections avec corpus vide ou incompatible sont exclues

Collections Publiques à Filtrer

Élément Endpoint API Modification
Corpus publics GET /api/corpus/public Filtrer par indexed_provider = current OR NULL
Sources publiques GET /api/sources/public Filtrer par indexed_provider = current OR NULL
Collections utilisateur GET /api/collections Filtrer les documents par provider

Fichiers à Modifier

Fichier Modification
app/features/corpus/router.py Endpoint public : ajouter filtre provider courant
app/features/sources/router.py Endpoint public : ajouter filtre provider courant
UI-FRONT/js/services/rag.js Afficher uniquement les collections compatibles
UI-FRONT/js/components/corpus-selector.js Filtrer la liste des corpus disponibles

UX Utilisateur

Affichage
  • L'utilisateur ne voit que les collections compatibles
  • Collections sans corpus = exclues (pas de contenu)
  • Filtrage transparent côté backend
Recherche RAG
  • Recherche utilise uniquement les collections du provider courant
  • Pas de mélange d'embeddings incompatibles
  • Performance optimale (pas de filtre post-recherche)

Section 7

Plan de Migration

↑ Sommaire

Étapes d'Implémentation

Phase 1 : Backend Repository
Ajouter filtre provider aux repositories (documents, sources, corpus)
Phase 2 : Backend Router
Modifier les endpoints de listing pour filtrer • Ajouter le provider courant dans les réponses API
Phase 3 : Frontend Admin (UI-BACK)
Afficher les badges provider • Ajouter l'indicateur global • Modifier les modales corpus
Phase 4 : Frontend Utilisateur (UI-FRONT)
Filtrer collections publiques • Sélecteur corpus compatible • Recherche RAG filtrée
Phase 5 : Tests et Documentation
Tests unitaires pour le filtrage • Tests E2E pour le changement de provider

Rétrocompatibilité

💡
Les éléments avec indexed_provider = NULL sont considérés comme "legacy". Ils sont affichés quel que soit le provider courant. Après réindexation, ils obtiennent le provider courant.
