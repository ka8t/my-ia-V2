Contexte & pré-requis

État de départ

V1 (`my-ia`) tourne en production sur le VPS 51.210.245.202, ports 3000 (UI front) et 8081 (UI back). V2 (`my-ia-V2`) est livrée complète localement (Phase 3.7-3.9), 209 tests verts, push sur origin/dev.

État cible

V2 est la production active sur le VPS, accessible aux mêmes credentials. V1 est arrêté (containers stoppés) mais code/BDD/ChromaDB conservés ≥ 30 jours pour rollback. Tag v2.0.0 sur main du repo V2.

Hors scope

Pas de migration de schéma BDD (V2 utilise les mêmes tables que V1 — les modèles SQLAlchemy ont été repris à l'identique depuis le tag v1.0.0-js-final). Pas de migration ChromaDB (mêmes collections, même vector store).

Pré-requis exécution

  • Accès SSH au VPS : ssh debian@51.210.245.202
  • Accès en écriture au repo ka8t/my-ia-V2
  • Branche dev verte (CI/local) avec tous les tests passants
  • Sauvegarde BDD V1 récente (≤ 24h)
  • Fenêtre de maintenance annoncée aux utilisateurs (recommandé)
⚠️ Lecture obligatoire avant 4.d. Le cutover (4.d) coupe l'accès utilisateur ~5-10 minutes. Toute modification BDD pendant cette fenêtre est perdue (V1 stoppé, V2 pas encore en ligne). Annoncer aux utilisateurs et privilégier une fenêtre creuse (nuit / week-end).

4.a

Audit de parité BDD V1 vs V2

Vérifier que les schémas SQL produits par V1 et V2 sont strictement identiques. Si différence, créer une migration Alembic V2 ou trancher pour Option B.

Étapes locales

  1. Démarrer V1 en local (port 5432) si pas déjà fait : 
    cd ~/Documents/Code/my-ia
./scripts/start.sh
  2. Démarrer V2 en local (port 5442) si pas déjà fait : 
    cd ~/Documents/Code/my-ia-V2
./scripts/start.sh
  3. Dump des schemas (DDL only, pas de données) : 
    docker exec my_ia_postgres pg_dump -U my_ia_db_user --schema-only --no-owner --no-acl my_ia_db > /tmp/schema_v1.sql
docker exec my_ia_v2_postgres pg_dump -U my_ia_v2_db_user --schema-only --no-owner --no-acl my_ia_v2_db > /tmp/schema_v2.sql
  4. Diff (filtre sur les noms de DB qui diffèrent) : 
    diff <(sed 's/my_ia_db/X/g; s/my_ia_db_user/Y/g' /tmp/schema_v1.sql) \
     <(sed 's/my_ia_v2_db/X/g; s/my_ia_v2_db_user/Y/g' /tmp/schema_v2.sql)
  5. Comparer les versions Alembic : 
    docker exec my_ia_postgres psql -U my_ia_db_user -d my_ia_db -tAc "SELECT version_num FROM alembic_version"
docker exec my_ia_v2_postgres psql -U my_ia_v2_db_user -d my_ia_v2_db -tAc "SELECT version_num FROM alembic_version"

Schémas non identiques mais convergents — V2 ajoute des améliorations qui seront appliquées via les migrations Alembic existantes lors du cutover.

Lignes du dump schema 1 636 1 731

Différences observées

  • V1 a en plus : TEST_TABLE (artefact de test, sera ignoré)
  • V2 a en plus :
    • Contraintes UNIQUE : system_configs_key_key, uq_cities_name_postal_country, ix_oauth_accounts_oauth_name_account_id
    • 17 nouveaux index (collections owner/type, context_sources enabled/type, conversations collection, documents collection, cities postal_code, password_history user_id, source_indexation_log ×3, system_configs category, users approval_status, users first_name_search_gin, users last_name_search_gin)
  • Évolutions de colonnes (V2 plus permissive ou plus performante) :
    • context_sources.config : json → jsonb
    • *.indexed_provider : varchar(20) → varchar(50)
    • Plusieurs colonnes NOT NULL rendues nullable (created_at, updated_at, current_version, account_email, health_status)
  • Régression possible : ix_system_configs_key est UNIQUE en V1 mais non-UNIQUE en V2. Compensé par la nouvelle contrainte system_configs_key_key UNIQUE qui couvre la même clé.

Verdict

  • ✅ Aucune table manquante en V2 côté production.
  • ✅ Aucun rename / drop column qui casserait les données existantes.
  • ✅ V2 a 14 migrations Alembic de plus que V1 (20260221_1945 → 20260505_1200). Lancer alembic upgrade head avec le code V2 sur la BDD V1 les appliquera toutes (création des index, contraintes UNIQUE, ALTER TYPE json → jsonb, ALTER varchar(20) → varchar(50)).
  • ✅ Option A (in-place) confirmée — pas besoin de migration custom. La séquence cutover est : stop V1 → run alembic upgrade head avec le code V2 → start V2.
✅ Livrable 4.a. Schémas non identiques mais convergents via les migrations existantes. Option A confirmée. Aucune migration custom à créer.

4.c

Smoke staging sur VPS

Déployer V2 sur le VPS en parallèle de V1 (ports staging 8090/8010/5442) et vérifier que tout fonctionne bout-en-bout sans toucher à V1.

Étapes

  1. Push sur main V2 (1ère fois, fast-forward depuis dev) : 
    git checkout main && git merge --ff-only dev && git push origin main && git checkout dev
  2. Préparer l'accès SSH GitHub depuis le VPS : deploy key dédiée (ed25519) + alias github-my-ia-v2 dans ~/.ssh/config du VPS.
  3. Cloner le repo dans /home/debian/my-ia-v2 sur le VPS.
  4. Créer le .env staging (chmod 600) avec secrets aléatoires + DEPLOY_ENV=dev (HTTP plain → cookie sans secure).
  5. Démarrer V2 : docker compose up -d --build.
  6. Vérifier les containers et l'état health : 
    docker compose ps
curl http://localhost:8090/health
  7. Smoke check via curl : login admin → /web/admin charge.
  8. Smoke check manuel dans un navigateur (à valider visuellement) :
    • Ouvrir http://51.210.245.202:8090/web/login
    • Login admin (admin@test.example / Admin123!) → atterrir sur /web/admin
    • Naviguer : Corpus, Sources, Système (LLM, RAG), Audit
    • Vérifier que V1 (ports 3000/8081) est toujours fonctionnel
  9. Smoke E2E Playwright pointé sur le VPS (optionnel) : 
    E2E_BASE_URL=http://51.210.245.202:8090 ./scripts/test/run.sh e2e

4.d

Cutover (fenêtre de maintenance)

🚨 Étape critique. Coupe l'accès utilisateur 5-10 min. Annoncer la fenêtre. Avoir un terminal SSH ouvert prêt au rollback.

T-0 : pré-checks

  1. Sauvegarde BDD V1 fraîche (T-0) : 
    ssh debian@51.210.245.202 "docker exec my_ia_postgres pg_dump -U my_ia_db_user my_ia_db | gzip" \
  > ~/backups/my_ia_pre_cutover_$(date +%Y%m%d_%H%M).sql.gz
  2. Sauvegarde ChromaDB : 
    ssh debian@51.210.245.202 "docker run --rm -v my_ia_chroma_data:/source -v /tmp:/dest alpine \
  tar czf /dest/chroma_pre_cutover_$(date +%Y%m%d_%H%M).tar.gz -C /source ."
  3. Confirmer absence d'utilisateurs actifs (logs nginx ou SELECT count(*) FROM sessions WHERE last_activity > now() - interval '5 min').

T+0 : bascule

  1. Stop V1 : 
    ssh debian@51.210.245.202 "cd /opt/my-ia && ./scripts/stop.sh"
  2. Si Option A : libérer les ports (3000, 8081) en arrêtant my_ia_ui_front, my_ia_ui_back. Modifier docker-compose.yml V2 pour mapper sur 3000 : 
    app:
  ports:
    - "3000:8080"  # remplace 8090:8080
  3. Reconfigurer le .env V2 sur le VPS pour pointer sur la BDD V1 (Option A) : 
    DATABASE_URL=postgresql+asyncpg://my_ia_db_user:<PASS>@my_ia_postgres:5432/my_ia_db
SANITIZED_PREFIX=my_ia_v2  # garde le prefix V2 pour les containers
    Note : ajouter my_ia_postgres au network du compose V2, ou utiliser host network.
  4. Re-démarrer V2 : 
    ssh debian@51.210.245.202 "cd /opt/my-ia-v2 && docker compose up -d --force-recreate"
  5. Vérifier health : 
    curl -k https://51.210.245.202:3000/health

T+5 : validation utilisateur

  1. Login admin via le navigateur sur l'URL historique (https://51.210.245.202:3000 ou domaine prod si DNS).
  2. Smoke critique : créer une conversation, uploader un document, lancer une recherche RAG.
  3. Vérifier les logs serveur (/web/admin/logs) — pas d'erreur 500 ni stacktrace.
  4. Si KO : déclencher rollback (section 8).
4.e

Cleanup post-cutover (après J+30)

git checkout main
git tag -a v2.0.0 -m "MY-IA V2.0.0 — première mise en production"
git push origin v2.0.0
  4. Mettre à jour MEMORY.md : V1 décommissionné, URL prod = celle de V2.
  5. Archiver le repo V1 sur GitHub (read-only).
  6. Déplacer PLAN-CUTOVER.html vers docs/Plans/Closed/.

Rollback global

Procédure d'urgence si V2 dysfonctionne en production. Cible : retour à V1 en moins de 5 minutes.

Rollback rapide (cohérence BDD préservée — Option A)

  1. Stop V2 : 
    ssh debian@51.210.245.202 "cd /opt/my-ia-v2 && docker compose down"
  2. Re-démarrer V1 : 
    ssh debian@51.210.245.202 "cd /opt/my-ia && ./scripts/start.sh"
  3. Vérifier health V1 : 
    curl -k https://51.210.245.202:3000/health
  4. Si la BDD a été modifiée par V2 et qu'une corruption est suspectée, restaurer depuis la sauvegarde T-0 : 
    gunzip -c ~/backups/my_ia_pre_cutover_*.sql.gz | \
  ssh debian@51.210.245.202 "docker exec -i my_ia_postgres psql -U my_ia_db_user my_ia_db"
⚠️ Décision de rollback. Documenter immédiatement la raison du rollback (logs, captures écran, requêtes erreur) AVANT de stop V2 — pour analyse post-mortem.
