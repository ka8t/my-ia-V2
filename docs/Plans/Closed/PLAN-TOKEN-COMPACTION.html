Pourquoi ce plan ? — Section 1

⬆ Sommaire

Le problème fondamental des LLM locaux

Les modèles LLM ont une fenêtre de contexte limitée :

ModèleContexte maxUsage typique
gemma2:2b8K tokens~6K utilisables
phi3:mini4K tokens~3K utilisables
llama3:8b8K tokens~6K utilisables
mistral:7b32K tokens~25K utilisables

Le contexte "utilisable" est inférieur au max car il faut réserver de la place pour :

  • Le system prompt (~200-500 tokens)
  • L'historique de conversation (~500-2000 tokens)
  • La réponse générée (~500-1500 tokens)
⚠️ Résultat : il ne reste que 2-4K tokens pour le contexte RAG.

Le dilemme actuel

Configuration actuelle : - top_k = 5 (chunks récupérés de ChromaDB) - max_context_items = 10 (chunks max envoyés au LLM) - Taille moyenne d'un chunk = 400 tokens → 5 chunks × 400 tokens = 2000 tokens de contexte RAG
❌ Problème 1
Avec seulement 5 chunks, on peut manquer des informations pertinentes dispersées dans le corpus.
❌ Problème 2
Si on augmente top_k à 15, on envoie 6000 tokens → le modèle sature et la qualité se dégrade.
✅ Solution
Compacter les chunks pour envoyer plus d'information en moins de tokens.
🔄

(score: 0.85, 380 tokens) │ ├── Chunk C : "Pour envoyer des mails..." (score: 0.82, 450 tokens) │ ├── Chunk D : "Le serveur SMTP doit..." (score: 0.78, 400 tokens) │ └── Chunk E : "Vérifiez la config SMTP..." (score: 0.75, 390 tokens) │ │ Total : 2040 tokens │ ▾ 4. CONSTRUCTION DU PROMPT │ │ ┌────────────────────────────────────────┐ │ │ System prompt (300 tokens) │ │ ├────────────────────────────────────────┤ │ │ Historique conversation (800 tokens) │ │ ├────────────────────────────────────────┤ │ │ Contexte RAG (2040 tokens) │ ← Les 5 chunks │ ├────────────────────────────────────────┤ │ │ Question utilisateur (20 tokens) │ │ └────────────────────────────────────────┘ │ │ Total envoyé au LLM : 3160 tokens │ ▾ 5. GÉNÉRATION LLM │ │ gemma2:2b génère la réponse (~500 tokens) │ ▾ 6. RÉPONSE À L'UTILISATEUR "Pour configurer SMTP dans MY-IA, allez dans..."

Où est le goulot d'étranglement ?

Étape 3 → Étape 4 : On récupère 5 chunks mais :

  • Certains chunks sont redondants (même info reformulée)
  • Certains chunks contiennent du bruit (phrases non pertinentes)
  • On ne peut pas augmenter top_k sans saturer le contexte

Pipeline avec compactage — Section 3

⬆ Sommaire

Le pipeline proposé ajoute une étape de compactage entre la récupération et l'envoi au LLM :

PIPELINE RAG AVEC COMPACTAGE (PROPOSÉ)
1. REQUÊTE UTILISATEUR │ ▾ 2. EMBEDDING DE LA REQUÊTE │ ▾ 3. RECHERCHE CHROMADB (top_k AUGMENTÉ) │ │ SELECT top_k=15 chunks WHERE similarity > 0.3 │ │ Résultat : 15 chunks, ~6000 tokens bruts │ ▾ ┌─────────────────────────────────────────────────────────────────────────────┐ │ 4. COMPACTAGE (NOUVELLE ÉTAPE) │ │ │ │ 4a. Déduplication sémantique │ │ - Calcul similarité entre les 15 chunks │ │ - Élimination des chunks avec similarité > 85% │ │ - Résultat : 10 chunks uniques (~4000 tokens) │ │ │ │ 4b. Extraction de phrases clés │ │ - Pour chaque chunk, garder les 3-5 phrases les plus pertinentes │ │ - Suppression des phrases d'introduction/transition │ │ - Résultat : 10 chunks compactés (~2000 tokens) │ │ │ │ Bilan : 15 chunks (6000 tokens) → 10 chunks (2000 tokens) │ │ = 67% de réduction, MAIS plus d'information couverte │ └─────────────────────────────────────────────────────────────────────────────┘ │ ▾ 5. CONSTRUCTION DU PROMPT │ │ Contexte RAG COMPACTÉ (2000 tokens) ← 10 chunks compactés │ (vs 5 chunks bruts avant) │ │ Total envoyé au LLM : 3120 tokens (similaire à avant) │ ▾ 6. GÉNÉRATION LLM → RÉPONSE

Cas d'usage concrets — Section 4

⬆ Sommaire
🟢 Cas 1 : Question simple
Q: "Quel est le port SMTP par défaut ?"

Avant compactage : 1 chunk suffit, réponse correcte
Après compactage : Idem, pas de différence notable

Gain : Minimal
🟢 Cas 2 : Question complexe
Q: "Compare SMTP vs API pour l'envoi d'emails"

Avant (5 chunks) :
• 3 chunks sur SMTP
• 2 chunks sur configuration
• 0 chunk sur API → Réponse incomplète

Après (15 → 10 compactés) :
• 4 chunks sur SMTP
• 3 chunks sur API
• 3 chunks sur comparaisons → Réponse complète
🟠 Cas 3 : Corpus redondant
Documentation avec reformulations :
• "Pour configurer SMTP, suivez ces étapes..."
• "La configuration du serveur SMTP se fait via..."
• "Les paramètres SMTP à définir sont..."

Avant : 5 chunks, 3 disent la même chose = gaspillage
Après : Déduplication → 1 chunk gardé, place pour d'autres infos

Gain : Maximal

        query=query,

    )

    # 2. NOUVEAU : Compacter
    if config.get("rag.compaction.enabled"):
        compactor = TokenCompactor(config)

    else:
        compacted_chunks = raw_chunks

    # 3. Limiter au max configuré
    return compacted_chunks[:config.get("sources.max_context_items")]

Corpus & Multi-Providers — Section 8

⬆ Sommaire

Architecture Corpus

Les chunks RAG peuvent provenir de plusieurs corpus et plusieurs collections :

Corpus "Documentation Technique" ├── Collection: doc_technique_ollama │ ├── Chunk A (doc: install.pdf) │ └── Chunk B (doc: config.pdf) └── Sources indexées └── Chunk C (source: wiki_interne) Corpus "FAQ Produit" └── Collection: faq_ollama ├── Chunk D (doc: faq.md) └── Chunk E (doc: troubleshoot.md) → Recherche RAG peut retourner : [A, D, B, E, C] provenant de corpus et documents différents

Règles de déduplication par corpus

La déduplication doit tenir compte du contexte d'origine :

ScénarioActionRaison
Chunks similaires du même document Dédupliquer Redondance réelle (chunking overlap)
Chunks similaires de documents différents (même corpus) Dédupliquer Information dupliquée dans le corpus
Chunks similaires de corpus différents Garder les deux Contextes potentiellement différents 
# Dans TokenCompactor._deduplicate()

async def _deduplicate(self, chunks: List[Dict]) -> List[Dict]:
    """
    Déduplique en tenant compte du corpus d'origine.
    """
    unique = []
    for chunk in chunks:
        is_duplicate = False
        for existing in unique:
            # Même corpus ? On peut dédupliquer
            if chunk.get("corpus_id") == existing.get("corpus_id"):
                similarity = self._cosine_similarity(
                    chunk["embedding"],
                    existing["embedding"]
                )
                if similarity > self.threshold:
                    is_duplicate = True
                    break
            # Corpus différents ? On garde les deux même si similaires
        if not is_duplicate:
            unique.append(chunk)
    return unique

Multi-Providers (Ollama / llama.cpp)

Les embeddings sont incompatibles entre providers car les modèles utilisent des espaces vectoriels différents :

🟦 Ollama
Modèle : nomic-embed-text:latest
Dimensions : 768
Collections : *_ollama

Les calculs de similarité pour la déduplication utilisent ces embeddings.
🟠 llama.cpp
Modèle : nomic-embed-text-v1.5.Q8_0.gguf
Dimensions : 768
Collections : *_llamacpp

Les embeddings sont dans un espace vectoriel différent.
⚠️ Contrainte : Le compactage ne peut comparer que des chunks provenant de collections du même provider. Une requête RAG interroge uniquement les collections *_ollama OU *_llamacpp selon le provider actif.

Implémentation recommandée

# Le compacteur reçoit déjà des chunks du bon provider
# car ChatService interroge les bonnes collections

class TokenCompactor:
    def __init__(self, config: dict, provider: str):
        self.provider = provider  # "ollama" ou "llamacpp"
        self.threshold = config.get("rag.compaction.similarity_threshold", 0.85)

    async def compact(self, chunks: List[Dict]) -> List[Dict]:
        # Les chunks ont déjà le champ corpus_id en metadata
        # On déduplique uniquement au sein du même corpus
        return await self._deduplicate_by_corpus(chunks)
