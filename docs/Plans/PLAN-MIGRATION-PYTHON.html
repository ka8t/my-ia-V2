Contexte & motivations

État actuel (v1.0.0-js-final)

  • Backend FastAPI mature — 18 features, RAG complet
  • 3 frontends JS séparés : UI-FRONT, UI-BACK, UI-SHARED
  • Système de templates maison (Templates.render())
  • Duplication de code entre admin et user
  • State management UI fragile (modules JS, pas de framework)

Pourquoi migrer ?

  • Réduire la surface de code : une seule stack
  • Cohérence types Pydantic ↔ rendu UI (pas de duplication)
  • Streaming natif (chat RAG) via HTMX SSE
  • Déploiement simplifié : un seul container web
  • Productivité : un seul langage à maintenir

Ce qu'on garde

  • Logique métier app/features/
  • Modèles SQLAlchemy + Alembic
  • Abstraction LLM (app/common/llm/)
  • Pipeline RAG (chunking, embeddings, ChromaDB)
  • Config en BDD (system_configs)
  • Locales fr/en (portés vers Jinja)

Ce qu'on jette

  • UI-FRONT/, UI-BACK/, UI-SHARED/
  • Containers nginx ui_front, ui_back
  • Templates JS (Templates.js)
  • Module icon-registry.js → macros Jinja SVG
  • Système d'i18n JS → Babel/jinja2 i18n

Stack cible

Backend (inchangé / consolidé)

  • Python 3.11+ — FastAPI
  • SQLAlchemy 2.0 async + Alembic
  • PostgreSQL 16 + ChromaDB
  • fastapi-users (JWT API + cookies session)
  • Ollama / llama.cpp

Frontend (nouveau)

  • Jinja2 — moteur de templates
  • HTMX — interactivité, SSE, partials
  • Alpine.js — micro-interactions DOM
  • CSS custom (réutilisé de UI-SHARED/css/)
  • SVG inline via macros Jinja

Tests

  • pytest (unit + integration)
  • Playwright (E2E HTML rendu)
  • httpx pour assertions HTTP

Dev tooling

  • ruff (lint + format)
  • mypy (typage strict)
  • pre-commit hooks
  • Docker / docker-compose
💡 Pourquoi Jinja2+HTMX plutôt que Reflex/NiceGUI ? HTMX permet une interactivité progressive sans runtime JS lourd. Reflex et NiceGUI génèrent un client React/Vue en arrière-plan : on perd le contrôle fin du DOM et on alourdit le bundle. Jinja2 reste l'outil natif FastAPI, le plus mûr et le plus simple à debug.

Hiérarchie

templates/

│   ├── base.html                # <html>, <head>, blocks: title, content, scripts
│   ├── auth.html                # extends base — layout login/register
│   ├── user.html                # extends base — layout app utilisateur
│   └── admin.html               # extends base — layout admin

├── pages/
│   ├── auth/{login,register,reset-password}.html
│   ├── chat/{conversation,history}.html
│   ├── documents/{list,upload,detail}.html
│   ├── admin/users/{list,detail}.html
│   └── admin/system/{llm,rag,storage,...}.html
│
├── partials/                    # Fragments rendus par HTMX (hx-target)
│   ├── chat/{message,suggestions,sources}.html
│   ├── tables/{users-row,documents-row}.html
│   └── notifications/toast.html
│
└── macros/
    ├── card.html                # {{ card(title, body, badge) }}
    ├── form.html                # {{ field(name, type, label, required) }}
    ├── table.html               # {{ table(headers, rows, sortable=True) }}
    ├── icon.html                # {{ icon('user') }} → SVG inline
    ├── badge.html               # {{ badge('active', color='success') }}
    └── toast.html               # {{ toast(level, message) }}

Mapping ancien → nouveau

Ancien (JS) Nouveau (Jinja2)
Templates.card({...}){{ card(title=..., body=...) }}
Templates.render('user-row', data){% include 'partials/tables/users-row.html' %}
Icons.userCircle(){{ icon('user-circle') }}
t('login.title'){{ _('login.title') }} (Babel)
showToast('success', t(...))HX-Trigger: showToast + {{ toast(...) }}
API call fetch() + render JShx-get / hx-post → partial Jinja

Règles d'or (V2)

  • Tout HTML rendu côté serveur via Jinja — jamais de manipulation DOM JS pour générer du contenu
  • Macros mutualisées : pas de HTML dupliqué entre pages
  • HTMX pour les updates : hx-get, hx-post, hx-swap
  • Alpine.js uniquement pour : toggles, dropdowns, modals locaux (pas de state global)
  • i18n : {{ _('cle') }} partout, jamais de texte hardcodé
  • Tableaux triables : via hx-get?sort=col (re-render serveur)
  • Toasts : Warning/Error persistants, Success/Info temporaires (CSS animation)
  • SVG icons : macro icon() + fichiers static/icons/*.svg chargés à build

Risques & mitigations

RisqueImpactMitigation
Streaming chat (SSE) plus complexe en HTMX qu'en JS natif Moyen Prototype avant phase 3 ; fallback WebSocket via fastapi-ws
Perte d'interactivité riche (drag&drop upload, autocomplete sources) Moyen Alpine.js + HTMX patterns ; isoler quelques composants en JS pur si besoin
i18n : 1900+ clés à porter de JSON vers Babel Faible Script de conversion automatique JSON → .po
Régression admin sur les 14 modules system/* Élevé Tests E2E Playwright systématiques + checklist par module
Performance rendu serveur vs JS Faible Cache fragments Jinja, HTMX hx-target pour partials
Bundle CSS volumineux à porter Faible Audit CSS au passage, suppression du non utilisé
