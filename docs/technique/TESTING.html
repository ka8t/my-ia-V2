Vue d'Ensemble — Section 1

L'infrastructure de tests MY-IA couvre l'ensemble de l'application :

🧱 ~100+ Tests Unitaires
Tests pour l'API et les fonctions métier, isolés avec mocking complet.
🔗 Tests d'Intégration E2E
Tests end-to-end avec services réels (PostgreSQL, ChromaDB, Ollama).
📜 Scripts Automatisés
Scripts pour endpoints HTTP (curl) et tests unitaires (pytest via Docker).
⚙️ CI/CD GitHub Actions
Pipeline complet avec lint, tests, coverage et security scan.
📊 Coverage 70%+
Coverage minimum requis de 70% sur l'ensemble du code.
🎭 Mocking Complet
Isolation complète des tests via mocks pour Ollama, ChromaDB, etc.

Scripts de Test — Section 3

1. Tests Unitaires (pytest) — run-tests.sh

Exécute les tests pytest dans le container Docker (obligatoire pour PostgreSQL/UUID).

# Afficher les modules disponibles
./scripts/test/run-tests.sh --list

# Lancer tous les tests
./scripts/test/run-tests.sh

# Lancer un module spécifique
./scripts/test/run-tests.sh admin       # Tests administration
./scripts/test/run-tests.sh user        # Tests utilisateur
./scripts/test/run-tests.sh auth        # Tests authentification
./scripts/test/run-tests.sh documents   # Tests documents
./scripts/test/run-tests.sh storage     # Tests stockage
./scripts/test/run-tests.sh crypto      # Tests cryptographie
./scripts/test/run-tests.sh geo         # Tests géolocalisation
./scripts/test/run-tests.sh sources     # Tests sources externes (125 tests)
./scripts/test/run-tests.sh speech      # Tests speech-to-text

# Options pytest
./scripts/test/run-tests.sh admin -v            # Mode verbose
./scripts/test/run-tests.sh -x                  # Stopper au premier échec
./scripts/test/run-tests.sh -k "test_create"    # Filtrer par pattern
./scripts/test/run-tests.sh admin --cov         # Avec couverture
./scripts/test/run-tests.sh --last-failed       # Rejouer les échecs

2. Tests Endpoints HTTP (curl) — test-endpoints.sh

Teste les endpoints de l'API via des requêtes HTTP réelles.

./scripts/test/test-endpoints.sh base           # Endpoints publics

./scripts/test/test-endpoints.sh chat           # Chat RAG (lent)

Exécution des Tests — Section 4

Tests Rapides (unitaires)

# Via le script (recommandé)
./scripts/test/run-tests.sh

# Ou directement dans Docker
docker-compose exec app python -m pytest tests/ -v

Tests Complets (avec intégration)

# Démarrer les services
docker compose up -d

# Tests unitaires
./scripts/test/run-tests.sh

# Tests endpoints HTTP
./scripts/test/test-endpoints.sh

Tests avec Coverage

./scripts/test/run-tests.sh --cov

# Ou directement
docker-compose exec app python -m pytest tests/ --cov=app --cov-report=term-missing

Tests Spécifiques

# Un fichier
./scripts/test/run-tests.sh tests/admin/test_admin_users.py

# Avec un pattern
./scripts/test/run-tests.sh -k "test_create"

# Un module
./scripts/test/run-tests.sh admin

Markers — Section 5

Les tests sont catégorisés avec des markers pytest :

# Tests unitaires seulement
pytest -m unit

# Tests d'intégration seulement
pytest -m integration

# Tests API
pytest -m api

# Tests du système d'ingestion
pytest -m ingest

# Tests sans les lents
pytest -m "not slow"

# Combiner les markers
pytest -m "unit and api"
unit
Tests unitaires isolés, rapides, avec mocking.
integration
Tests d'intégration avec services réels.
api
Tests des endpoints HTTP de l'API.
slow
Tests lents (appels Ollama, etc.).
ingest
Tests du système d'ingestion de documents.

Écrire de Nouveaux Tests — Section 8

Test Unitaire

import pytest

@pytest.mark.unit
class TestMaFonction:
    def test_comportement_normal(self, client, test_api_key):
        """Vérifie le comportement normal"""
        response = client.post(
            "/endpoint",
            json={"data": "test"},
            headers={"X-API-Key": test_api_key}
        )

        assert response.status_code == 200
        assert "expected_key" in response.json()

Debugging et Problèmes — Section 10

Commandes de Debug

Afficher les Prints

pytest -s

Mode Debug (pdb)

pytest --pdb

Logs Détaillés

pytest --log-cli-level=DEBUG

Re-runner les Échecs

pytest --lf  # Last failed
pytest --ff  # Failed first

Ou dans le code :

import pdb; pdb.set_trace()

Tests qui passent localement mais échouent en CI

  • Chemins — Vérifier les chemins (absolu vs relatif)
  • Variables — Vérifier les variables d'environnement
  • Versions — Vérifier les versions Python
  • Services — Vérifier les services (Ollama, ChromaDB)

Timeout en Tests d'Intégration

# Augmenter le timeout
pytest --timeout=300

# Utiliser un modèle plus léger
export MODEL_NAME="tinyllama"

ChromaDB Non Accessible

# Vérifier le conteneur
docker ps | grep chroma

# Redémarrer
docker compose restart chroma

# Vérifier les logs
docker compose logs chroma

Bonnes Pratiques

  • Tests isolés — Chaque test doit être indépendant
  • Noms descriptifs — test_chat_rejects_invalid_api_key
  • Une assertion principale — Focus sur un comportement
  • Utiliser les fixtures — Éviter la duplication
  • Mocker les dépendances — Isoler le code testé
  • Documenter les tests — Docstrings claires
  • Skip intelligemment — pytest.skip() si services down
