1 Vue d'ensemble

Les collections sont le mécanisme central d'organisation des contenus dans MY-IA. Elles font le lien entre les données métier (PostgreSQL) et le stockage vectoriel (ChromaDB).

┌─────────────────────────────────────────────────────────────────────────────┐ │ BASE DE DONNÉES (PostgreSQL) │ ├─────────────────────────────────────────────────────────────────────────────┤ │ Collection (table `collections`) │ │ ├── id, name, display_name, type (public/private) │ │ ├── owner_id (null si public, user_id si privée) │ │ └── corpus_id (relation 1-1 avec un corpus) │ │ │ │ Corpus (table `corpus`) │ │ └── Regroupe Documents + Sources │ │ │ │ Documents / Sources │ │ └── Contenu textuel découpé en chunks │ └─────────────────────────────────────────────────────────────────────────────┘ │ ▼ ┌─────────────────────────────────────────────────────────────────────────────┐ │ CHROMADB (Vectoriel) │ ├─────────────────────────────────────────────────────────────────────────────┤ │ Collection ChromaDB = nom_collection + "_" + provider │ │ │ │ Exemple pour "public_docs" : │ │ ├── public_docs_ollama (embeddings générés par Ollama) │ │ └── public_docs_llamacpp (embeddings générés par llama.cpp) │ │ │ │ Contient : chunks (texte) + embeddings (vecteurs) + métadonnées │ └─────────────────────────────────────────────────────────────────────────────┘

2 Concepts clés

Collection PostgreSQL vs Collection ChromaDB

Aspect Collection PostgreSQL Collection ChromaDB
Rôle Entité métier (organisation) Stockage vectoriel (recherche)
Contenu Métadonnées, relations Chunks + embeddings
Nommage public_docs public_docs_ollama
Multiplicité 1 collection N collections (1 par provider)

Pourquoi un suffixe par provider ?

Les embeddings sont incompatibles entre providers :

Provider Modèle embedding Dimensions Espace vectoriel
Ollama nomic-embed-text 768 Propre à Ollama
llama.cpp nomic-embed-text-v1.5.Q8_0.gguf 768 Différent
Conséquence : Un chunk indexé avec Ollama ne peut pas être recherché avec llama.cpp. Chaque provider nécessite sa propre collection ChromaDB.

5 Vue Admin vs Vue User

Interface Administration (UI-BACK)

Accès complet :

  • Toutes les collections (publiques + privées de chaque user)
  • Statistiques détaillées (chunks, documents, sources)
  • État d'indexation par provider (Ollama, llama.cpp)
  • Modèle d'embedding utilisé
  • Alertes de mismatch (modèle différent du modèle actif)

Actions disponibles :

  • Créer collection publique
  • Assigner/modifier le corpus
  • Voir l'état d'indexation par provider
  • Réindexer pour un provider spécifique
  • Vider / Supprimer une collection
  • Synchroniser les compteurs

Interface Utilisateur (UI-FRONT)

Accès limité :

  • Collections publiques autorisées
  • Sa propre collection privée

Ne voit pas :

  • Collections privées des autres utilisateurs
  • Détails techniques (provider, ChromaDB, embeddings)
  • Statistiques admin

Actions disponibles :

  • Uploader des documents (→ collection privée)
  • Gérer ses documents (supprimer, télécharger)
  • Sélectionner les collections pour le RAG
  • Poser des questions

7 Gestion multi-provider

Problématique

Changer de provider LLM (Ollama ↔ llama.cpp) implique :

  1. Les embeddings existants sont incompatibles
  2. La recherche RAG ne fonctionne plus
  3. Il faut réindexer avec le nouveau provider

Solution : Collections suffixées

Collection PostgreSQL: "documentation" │ ├── ChromaDB: "documentation_ollama" (embeddings Ollama) │ └── ChromaDB: "documentation_llamacpp" (embeddings llama.cpp)

État d'indexation (Admin UI)

┌─────────────────────────────────────────────────────────────┐ │ État d'indexation - Documentation Technique │ ├─────────────────────────────────────────────────────────────┤ │ │ │ ┌─────────────────────────────────────────────────────┐ │ │ │ OLLAMA [Actif] │ │ │ │ ✓ 1,234 chunks │ │ │ │ Modèle: nomic-embed-text │ │ │ │ [Réindexer] │ │ │ └─────────────────────────────────────────────────────┘ │ │ │ │ ┌─────────────────────────────────────────────────────┐ │ │ │ LLAMA.CPP │ │ │ │ ✗ Non indexé │ │ │ │ │ │ │ │ [Indexer] │ │ │ └─────────────────────────────────────────────────────┘ │ │ │ └─────────────────────────────────────────────────────────────┘

Workflow typique

  1. Configuration initiale : Provider = Ollama
  2. Indexation : Documents indexés dans {collection}_ollama
  3. Changement provider : Admin passe à llama.cpp
  4. Alerte : UI affiche "Réindexation nécessaire"
  5. Réindexation : Admin lance réindex pour llama.cpp
  6. Résultat : {collection}_llamacpp créée et peuplée

10 Opérations de vidage (Clear Index)

Concept

L'opération "Vider" (Clear Index) supprime uniquement les chunks de ChromaDB :

  • Conserve les fichiers sur le disque
  • Conserve les enregistrements en base de données
  • Met à jour les compteurs (chunk_count = 0)
  • Supprime les embeddings de tous les providers

Endpoints API

Entité Endpoint Cascade
Collection DELETE /api/admin/collections/{id}/index Documents de la collection
Document DELETE /api/admin/documents/{id}/index -
Source DELETE /api/admin/sources/{id}/index -
Corpus DELETE /api/admin/corpus/{id}/index Documents + Sources

Code commun (DRY)

Les fonctions de vidage sont centralisées dans app/common/utils/chroma_helpers.py :

# Vider par filtre (générique)
clear_chunks_by_filter(chroma, collection_name, where_filter, provider=None)

# Vider un document (tous providers)
clear_document_chunks(chroma, collection_name, document_hash)

# Vider une source (tous providers)
clear_source_chunks(chroma, source_name)

# Vider une collection (tous providers)
clear_collection_all_providers(chroma, collection_name)

Différence avec "Supprimer"

Action ChromaDB Fichiers Base de données
Vider Supprimé Conservé Conservé (compteurs = 0)
Supprimer Supprimé Supprimé Supprimé

11 Schéma BDD

-- Table principale
CREATE TABLE collections (
    id UUID PRIMARY KEY,
    name VARCHAR(255) UNIQUE NOT NULL,      -- Nom technique
    display_name VARCHAR(255) NOT NULL,     -- Nom affiché
    description TEXT,
    type VARCHAR(20) NOT NULL,              -- 'public' ou 'private'
    owner_id UUID REFERENCES users(id),     -- NULL si public
    corpus_id UUID REFERENCES corpus(id),   -- Relation 1-1
    space VARCHAR(20) DEFAULT 'cosine',     -- Espace vectoriel
    embedding_model VARCHAR(255),           -- Dernier modèle utilisé
    document_count INT DEFAULT 0,
    chunk_count INT DEFAULT 0,
    created_at TIMESTAMP,
    updated_at TIMESTAMP
);

-- Index
CREATE INDEX idx_collections_type ON collections(type);
CREATE INDEX idx_collections_owner ON collections(owner_id);

12 Troubleshooting

"Aucun résultat RAG"

  1. Vérifier que la collection a des chunks (chunk_count > 0)
  2. Vérifier l'état d'indexation pour le provider actif
  3. Réindexer si changement récent de provider

"Embedding mismatch warning"

Le modèle d'embedding actuel diffère de celui utilisé pour indexer :

  1. Les résultats RAG peuvent être dégradés
  2. Solution : réindexer la collection

"Collection ChromaDB introuvable"

Fallback automatique vers nom legacy (sans suffixe) :

  1. Recherche: {name}_{provider} → 404
  2. Fallback: {name} → trouvé
  3. Log: "Using legacy collection"
