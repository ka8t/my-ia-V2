9.1 Détection automatique du mode de réponse ⏳

Objectif : Adapter automatiquement le style de réponse (conversationnel vs formel) selon la nature de la question utilisateur, tout en conservant le RAG actif.

💡 Deux modes de réponse :
Chatbot : Style conversationnel, amical, décontracté (salutations, questions simples, bavardage)
Assistant : Style formel, structuré, professionnel (questions techniques, demandes d'analyse, tâches)

Architecture proposée

  • ⬜ Détection backend : Fonction detect_response_style(query) dans rag_config.py
  • ⬜ Patterns de détection : Salutations, questions courtes, mots-clés formels, longueur, ponctuation
  • ⬜ System prompts dynamiques : Injection du style dans le prompt selon le mode détecté
  • ⬜ Override utilisateur : Toggle UI ou préfixe (/chat, /assistant) pour forcer un mode
  • ⬜ Préférence utilisateur : Mode par défaut configurable en BDD (user_preferences)
  • ⬜ Retour API : Champ response_style_used dans la réponse streaming

Critères de détection

→ Mode Chatbot
  • Salutations : "bonjour", "salut", "ça va", "hello"
  • Questions < 5 mots sans mots techniques
  • Emojis présents
  • Ton informel détecté
→ Mode Assistant
  • Mots-clés : "analyse", "compare", "explique", "détaille"
  • Questions > 10 mots ou techniques
  • Demandes de listes, tableaux, code
  • Référence à des documents/sources

  • app/features/chat/service.py — Intégrer détection avant appel LLM
  • app/features/chat/schemas.py — Ajouter response_style dans ChatRequest/ChatResponse

14.2 Catégories de logs

Chaque catégorie répond à un objectif distinct. Toutes doivent être identifiables par un champ log_category dans le JSON.

⚙️ Logs techniques (application)
Exceptions, erreurs métier, temps de réponse, appels à des services externes (Ollama, ChromaDB), timeouts, stack traces. Objectif : debug et exploitation au quotidien.
🌐 Logs d'accès (access logs)
Chaque requête entrante/sortante : URL, méthode HTTP, code de réponse, durée, IP source, identifiant de corrélation (request_id). Objectif : monitoring, capacité, performance.
📋 Logs d'audit
Qui a fait quoi, quand, sur quelles données : création/suppression/modification d'objets, changements de droits, export de données. Objectif : sécurité, conformité (RGPD, SOX).
Champs obligatoires : sujet (qui), action (quoi), ressource (sur quoi), quand, depuis où (IP/appareil), motif éventuel.
🔒 Logs de sécurité
Authentifications réussies/échouées, élévations de privilèges, tentatives d'accès interdit, changements de configuration sensibles. Objectif : détection d'intrusions, forensics.
📡 Logs d'infrastructure
Santé des serveurs/containers (CPU, mémoire, disque), redémarrages, déploiements, événements Docker. Objectif : corréler problèmes applicatifs et infra.

14.3 Niveaux de sévérité

Hiérarchie standard à utiliser pour toutes les catégories de logs :

NiveauValeurDescriptionProduction
TRACE 5 Flux d'exécution très détaillé, variables intermédiaires Désactivé
DEBUG 10 Informations de diagnostic pour les développeurs Désactivé
INFO 20 Événements normaux importants : démarrage service, traitement réussi, tâches planifiées Actif
WARN 30 Anomalie potentielle non bloquante : timeout ponctuel, fallback, valeur inattendue gérée Actif
ERROR 40 Échec d'une opération fonctionnelle ou technique, nécessite intervention Actif
FATAL / CRITICAL 50 Panne critique du service : impossible de démarrer, perte de ressource essentielle Actif
⚠️ Règle de configuration : En production, le niveau minimum doit être INFO pour les logs techniques/accès/infrastructure et WARN au minimum pour les logs d'audit et de sécurité (ces derniers sont toujours actifs, jamais filtrés en dessous de WARN). TRACE et DEBUG sont réservés au développement ou à un périmètre restreint activé temporairement via l'admin.

Externalisation templates HTML/SVG — Section 17 — PRIORITÉ MOYENNE

⬆ Sommaire

✅ Terminé Plan détaillé : PLAN-TEMPLATES-ADMIN.html

Actuellement, de nombreux fragments HTML et SVG sont construits dynamiquement dans les fichiers JavaScript des deux interfaces (UI-FRONT et UI-BACK) via des concaténations de chaînes ou des template literals. Cela rend la maintenance difficile : modifier une icône SVG, un layout de carte ou un formulaire nécessite d'entrer dans le code JS et de comprendre la logique métier environnante.

17.1 Problème actuel

  • SVG inline dans le JS — Les icônes SVG (boutons, badges, indicateurs) sont écrites directement dans les chaînes JavaScript, mélangées avec la logique applicative
  • HTML dynamique — Des blocs HTML complets (cartes, listes, formulaires, bannières, modales) sont générés par concaténation dans les modules JS
  • Duplication — Certains fragments sont dupliqués entre UI-FRONT et UI-BACK sans être mutualisés dans UI-SHARED
  • Maintenabilité réduite — Un designer ou intégrateur ne peut pas modifier le markup sans risquer de casser la logique JS

17.2 Objectif

Extraire les fragments HTML et SVG générés dynamiquement vers des fichiers templates séparés, consultables et modifiables sans toucher au code JavaScript, tout en maintenant les performances (pas de requêtes HTTP supplémentaires à chaque rendu).

17.3 Approches possibles

📄 Éléments <template> HTML
Regrouper les fragments dans des balises <template id="tpl-xxx"> dans le HTML principal ou dans des fichiers inclus. Le JS clone le contenu via document.getElementById('tpl-xxx').content.cloneNode(true). Avantage : natif, zéro requête HTTP, performant.
📦 Fichiers .html préchargés
Fichiers templates dans UI-SHARED/templates/, chargés une seule fois au démarrage via fetch() et mis en cache dans un registre global (TemplateRegistry). Les rendus ultérieurs utilisent le cache sans requête. Avantage : séparation nette, fichiers éditables indépendamment.
🎭 Bibliothèque d'icônes SVG
Centraliser tous les SVG dans un sprite SVG ou un fichier icons.js exportant un objet { iconName: '<svg>...' }. Le JS référence les icônes par nom plutôt que par markup. Avantage : cohérence, réutilisabilité, catalogue visuel possible.
💡 Performance : quelle que soit l'approche retenue, les templates doivent être chargés/parsés une seule fois au démarrage et mis en cache en mémoire. Le rendu doit se faire par clonage ou interpolation de chaînes cachées, sans appels réseau supplémentaires.

17.4 Périmètre

InterfaceType de contenuExemples

Chaque fragment HTML ou icône SVG ne doit être défini qu'à un seul endroit. Avant de créer un nouveau template, vérifier systématiquement s'il existe déjà dans le registre partagé. Un template spécifique à une seule UI peut rester dans son dossier, mais dès qu'il est réutilisé par l'autre, il doit être remonté dans UI-SHARED/.
